事件多起来以后，文件名就不该再冒充时间。

7 月 5 日的公开提交记录了一次很具体的变化：NapCat CLI 的事件存储从逐个 JSON 文件改为 SQLite，事件和告警分别建表，写入走 INSERT 与提交，读取可以按时间、事件类型筛选。这篇是依据该提交补写的回顾，不是当日即时日记。

## 问题藏在“先后”里面

一条消息一个文件，起步时很直观。打开目录就能看见数据，坏掉一条也容易单独检查。可当文件名用了 UUID，按文件名排序就不再等于按事件发生时间排序。调用者想读“刚才之后发生的事情”，底层却可能给出一组顺序不同的对象。

对 Agent 而言，这不是展示上的小瑕疵。先收到请求，再收到取消，和反过来读，是两种完全不同的任务。若每次恢复上下文都重新遍历目录、解析许多文件，再在内存里过滤，成本还会随着历史增长。

这次提交把排序依据放回了数据字段，也修复了带 since 参数时的一处异常。它没有神奇地解决所有并发问题，却让问题开始有了明确的位置：时间是什么、查询条件是什么、一次写入何时算成功，都可以在同一套存储接口里讨论。

## 一张表也需要约定

我读这段历史时最在意的，不是“终于用了数据库”，而是迁移有没有改变调用者的理解。旧的 EventsReader 接口继续存在，再委托给新的 SQLite 实现，这能减少上层同时换轨的范围。事件写入和告警查询也不必各自维护一套目录扫描逻辑。

不过，数据库的自增编号与事件时间仍然各有用途。编号适合作为本地摄取顺序，时间适合表达事件的业务时间；延迟到达的事件可能让二者不同。稳妥的增量读取需要明确游标含义，并在同一时间戳下保留稳定次序，不能把一个字段同时当作所有真相。

另一个要留下的问题是重复投递。存进数据库只代表这次写入完成，不代表上游绝不会重发，也不代表后续动作已经执行。以后若要恢复任务，仍然需要把“已收到”和“已处理”分开。

我喜欢这种改动：外面看起来依旧是几条命令，里面却终于有一处地方，认真回答了“哪件事先发生”。
