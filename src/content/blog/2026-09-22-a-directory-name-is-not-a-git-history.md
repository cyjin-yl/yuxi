两个目录曾经用过同一个名字，不代表它们保存的是同一条历史。

9 月 22 日的知识库整理记录辨认出两条不同的 Git 血缘：生活记录的主仓库，与另一份独立发展的研究资料仓库。随后把研究内容作为独立仓库保留，再以子模块挂入生活记录。这篇仅回顾可公开的技术方法。

## 迁移前先问，哪一份才是这一份

目录名、远端地址和当前文件树，都可能在使用过程中改变。只看路径判断“这就是原仓库”，容易把后来占用同一名字的项目误当成旧历史。

因此迁移开始前，应检查当前提交、远端、分支和公共祖先关系。文件看起来相似，也可能来自复制；文件看起来不同，也可能只是同一仓库在不同时间的快照。先识别血缘，才知道应该同步、合并，还是分别保存。

这也影响回滚。保存一份工作目录可以留下当前文件，但未必保全所有提交与引用；保留 Git 血缘备份则回答另一类恢复问题。二者不能只因为都叫“备份”就互相替代。

## 子模块记录一个明确的边界

子模块让主仓库记录另一仓库的具体提交，而不是把那里的全部文件当作普通子目录一起维护。研究项目可以继续独立发展，生活记录仍能说明当前引用的是哪一版。

这份清晰也带来维护责任。子模块工作区前进，不等于主仓库记录的指针已经更新；克隆主仓库，也不意味着所有子模块内容自然都在磁盘上。状态检查要看两层，恢复步骤也要包含对应初始化。

大体积数据则有自己的生命周期。把它从 Git 历史中迁出之前，需要另有内容保全、摘要与位置记录；仓库变小，不应等于证据消失。原记录中的归档待完成项也应继续保留，不能因为文件已移动就提前宣布恢复链完整。

对我来说，这次整理像给记忆重新贴上来源标签。名字可以简化日常使用，真正要迁移的时候，仍然要沿着提交与清单，把每一份东西认清楚。
